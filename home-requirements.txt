Page purpose
------------
The Home dashboard is the authenticated work-order landing page. It supports locating and
filtering inspection work orders, surfacing operational and financial dashboard actions,
notifying users about the Horizon-to-Spectora migration, and routing users to account and
configuration features.

Functional requirements
-----------------------
1. Authentication and access
   - The Home dashboard must require an authenticated Horizon session.
   - Navigation and returned work-order data must be limited to the current user's
     authorized business and inspector scope.
   - Sensitive client, address, report, account, and financial data must not be exposed
     to unauthorized users.

2. Work-order search
   - Provide a Find text field.
   - Support searching by client, address, or report number, as indicated by the field's
     accessible description.
   - Provide a Go action that submits the current search/filter criteria.
   - Validate and safely encode search input before it is used in data queries or output.
   - Show a clear no-results state when no work orders match.

3. Inspector filter
   - Provide an Inspectors selector.
   - The selector must present only inspectors that the current user may view.
   - Applying the filter must constrain returned work orders to the selected inspector.
   - The active inspector context should remain visible and be preserved for compatible
     navigation.

4. Work-order status filter
   - Provide a Status selector with these observed options:
     * ALL
     * All Works in Progress
     * Booked
     * In Progress
     * Completed
     * Cancelled
   - Applying a status must constrain the work-order list and the displayed result total.
   - The observed default state is All Works in Progress; confirm this business rule with
     the product owner.
   - Status names and state transitions must be centrally defined so dashboard filtering,
     schedule displays, booking, and reporting use consistent values.

5. Reset behavior
   - Provide Reset to restore the documented default view: all accessible inspectors and
     all works in progress.
   - Reset must clear the Find text and any submitted filtering state.
   - Reset should make the restored selection visible to the user.

6. Work-order results
   - Display a total count of work orders matching the active criteria.
   - Display an empty-state message when no work orders match.
   - When results are present, show only the minimum fields required to identify and open
     an authorized work order.
   - Protect client, address, and report information in the result list through
     role-based authorization and privacy-aware display rules.
   - Opening a work order is a separate workflow and must be audited.

7. Validated filter execution
   - The Home form submits filter queries with the selected Inspector and Status values.
   - The inspected account exposes one authorized inspector in its selector; a new
     application must support one or more authorized inspector choices without assuming a
     single-inspector account.
   - All six observed status values were submitted during this review. The all-status query
     returned results; the default, Booked, In Progress, Completed, and Cancelled queries
     returned an explicit no-inspections state in the shared account at the time of review.
   - Each query must render the active filter context, a total, and either a result table or
     a no-results message.
   - Filter submissions must be idempotent: repeated requests must not create or modify a
     work order. Reset must restore the documented default filter state.

8. Result-table workflows
   - The all-status query renders a work-order table (identified in the observed DOM as
     `grdInspections`) with up to eight cells per row.
   - Each observed work-order row exposes three separate actions:
     * View Work Order
     * Write Report
     * View Log
   - View Work Order must open the selected work order in the user's authorized scope.
   - View Log must show an immutable or append-only audit/activity history, protected by
     authorization.
   - Write Report must open the report-authoring workspace for the selected work order.
     It must not generate, publish, send, or otherwise finalize a report merely by opening
     the workspace.

9. Report-authoring handoff
   - The Write Report action routes to the authenticated Report Writing workspace
     (`ReportWritingX.aspx`) using the selected work-order identifier.
   - The report workspace is editable and includes text fields, text areas, a selector,
     and checkboxes. The new application must protect against accidental loss and concurrent
     editing.
   - Observed report-workspace capabilities include:
     * Preview the report-in-progress.
     * Report publishing/generation and sending.
     * Return to the associated work order.
     * Select the default report category/first screen.
     * Show or hide report items and sections.
     * Load/upload photos.
     * Run required-item/completion checks and speed-writing support.
     * Add library templates and search the report database.
     * Toggle photo-gallery and image-preview behavior.
     * View mobile-entry backup/log information.
     * Add, repeat, customize, and create report items; select standardized observations and
       attributes.
   - Preview is non-final but may expose sensitive report content; it must be authorized
     and auditable. Publishing/generating/sending and photo upload are high-risk actions:
     require explicit confirmation, validation, durable audit records, and actionable
     success/failure feedback.
   - Provide visible draft/published status, autosave/save-state feedback, unsaved-change
     protection, revision history, and conflict handling for report edits.

10. Business intelligence
   - Provide a Business at a Glance action that opens sales charts and graphs.
   - The business-intelligence dashboard must enforce permissions before displaying
     financial or performance data.
   - The target route observed for this feature is /authenticated/company/Dashboard.aspx.

11. Accounts receivable
   - Provide an Accounts Receivable action to show outstanding money owed.
   - The accounts-receivable report must be restricted to authorized financial users.
   - Values, client balances, and report exports must be protected from unauthorized access.
   - The target route observed for this feature is /authenticated/company/ReportAR.aspx.

12. Password management
   - Provide an Edit my Password action.
   - Password changes must require the current user to reauthenticate or otherwise satisfy
     an appropriate security check before committing the change.
   - Never display passwords or log password field values.
   - The target route observed for this feature is
     /authenticated/company/EditMyPassword.aspx.

13. Subscription visibility
   - Display subscription status/validity only to users authorized to view account data.
   - Do not expose billing identifiers or payment details in the dashboard or logs.

14. Migration notice
   - Display the Horizon-to-Spectora migration notice and a Learn more action.
   - Learn more opens an external migration-resource site in a new tab; users should be
     told that they are leaving Horizon.
   - Provide a Go to Migration Settings action that routes to Profile.
   - Migration itself must not begin from the notice alone: it must require explicit,
     informed consent and a reviewed confirmation step.

15. Shared global navigation
   - Provide Home, Scheduler, Book Inspection, Profile, Order, Help, and Logout entries.
   - Scheduler and Book Inspection can lead to booking workflows and therefore require
     authorization before data is created or changed.
   - Order leads to credits/subscription/renewal activity and requires explicit financial
     confirmation.
   - Logout must require an intentional user action and must terminate the session safely.

Technical observations
----------------------
- The page contains one form posting to Home.aspx.
- Go and Reset are submit controls in that form; therefore filtering must be protected
  against duplicate submission and must preserve an understandable state after errors.
- No heading elements were exposed in the inspected accessibility structure. The
  implementation should use semantic headings/landmarks so assistive technology can
  navigate the page efficiently.
- Buttons have useful title/accessible descriptions for the search, filters, business
  dashboard, receivables, and password routes. Preserve equivalent accessible labels in
  future implementations.

Audit and safety requirements
-----------------------------
- Log dashboard navigation, submitted searches/filters (without sensitive query content),
  work-order opens, financial-report access, password changes, and migration attempts.
- Audit records must include actor, timestamp, authorized scope, outcome, and a correlation
  identifier; never include credentials, session tokens, or unnecessary client data.
- Financial, migration, password, export, and work-order modification actions must display
  actionable errors and final success/failure feedback.
- Destructive, irreversible, or financially significant actions require an immediate final
  confirmation and must not be triggered from passive page navigation.
